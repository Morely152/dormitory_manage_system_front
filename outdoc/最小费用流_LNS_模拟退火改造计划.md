# 排寝算法改造计划：最小费用流 + Repair + LNS + 模拟退火

## 目标

将 /accommodation/bed-allocation-new 从浏览器内的“贪心生成 + 模拟退火”改为 Flask 服务中的可行性优先求解器。新流程必须先产出一份所有学生均已落床的合法初始方案；只有在该方案存在后，才进行大邻域搜索（LNS）和模拟退火（SA）以优化软目标。

“一定能安排进去”的可验证口径不是原始总床位数，而是：在选定校区/研究生楼栋范围内，扣除已入住、不可分配、预留、锁定后的可用床位，经过寝室性别约束后的可用容量，能够覆盖男女学生需求。学院关系、最大插空比、苑区偏好、楼栋优先级和整间住满默认不得再造成“无解”。

## 现状与改造边界

- BedAllocationNewView.vue 负责参数、缓存、锁定、热力图、预览和导出；本科生和研究生均调用 Flask 服务。
- occupancyData.js 已统一床位、寝室、性别、入住和可分配状态，是后端输入规范的来源。
- bedAllocationNew.js 保留为遗留回归基线；页面不再调用其中的贪心或前端退火实现。
- 热力图、预览和 Excel 导出依赖快照的 assignments 与 rooms[].allocations，改造首期保持其字段兼容；只将 algorithm.version 升为 allocation-mcmf-lns-sa/v1，并增加求解证书字段。

## 约束分层

### 硬约束：任何阶段都不可突破

1. 每位学生恰好分配一张真实、唯一的床位；寝室人数不超过床位数。
2. 床位必须为 AVAILABLE，且床位/寝室的 assignable、active 标记均为真；已有学生、失效床位和满房不可使用。
3. 不得男女混住：部分入住寝室必须匹配现有住户性别；空寝室在求解前固定为一个性别，不能被两种性别同时使用。
4. 校区和学历范围不得越界；研究生仅能使用操作者选定的优先/后备楼栋集合。
5. 已锁定研究生方案、明确的整间锁定、明确的苑区预留必须保留。若预留希望在容量紧张时可被借用，必须显式切换为软预留。
6. 输入中的学生性别、床位/寝室标识和容量必须可解析；无法确定时作为数据质量错误，而不是由算法猜测。
7. 北苑学院性别互斥：同一学院在北苑的本次计划和已锁定研究生方案只能出现一种性别；已入住老生不参与学院维度检查，仅用于部分入住寝室的性别判断。

### 软目标：允许付出费用，不得导致初始无解

| 目标 | 现有默认权重 | 新求解中的含义 |
| --- | ---: | --- |
| 批次跨苑区分散 | 100 | 同一学院 × 性别 × 学历批次越分散，费用越高；不比较男女之间的苑区 |
| 批次指定苑区外安置 | 10 | 每名不在其所属学院 × 性别 × 学历批次指定苑区的学生计费 |
| 批次跨楼栋/跨寝室 | 1 / 4 | 鼓励同一学院 × 性别 × 学历批次集中，但允许拆分 |
| 空寝室碎片床位 | 0.1 | 尽量减少未住满空房的空床 |
| 未住满空寝室 / 单人空寝 | 2 / 35 | 强烈鼓励合寝与整间住满 |
| 学院不兼容混住 | 10（可配置） | 不再阻断可行性；对历史住户和本次计划混住分别计费 |
| 超过最大插空比 | 新增 | 将“最大值”变为高额但有限的分段费用，优先满足目标、资源不足时自动突破 |
| 未选优先苑区/楼栋 | 新增 | 偏好费用；研究生后备楼栋按顺序递增费用 |

所有硬约束由统一 validate_plan() 校验；任何搜索操作只要不通过校验即回滚，绝不依赖“足够大的费用”模拟硬约束。

## 已确认的 MCMF 边费用

MCMF 的所有费用均为非负整数。为避免“喜欢插空而不去空房”，全空房整间的费用必须严格低于同苑区同学院插空；学院/房间级的非线性质量留给 LNS 和 SA。

所有苑区语义均按学院 × 性别 × 学历批次独立处理。男生批次和女生批次即使属于同一学院，也不存在“应当同苑区”的费用或约束；两者可以在不同苑区分别取得各自最优解。

| 候选边 | 费用 | 适用条件 |
| --- | ---: | --- |
| 全空房、指定苑区 | 0 | 学院 × 性别明确指定该苑区 |
| 全空房、同苑区 | 1 | 未指定苑区时，位于该学院 × 性别 × 学历批次自身主苑区的基准全空房 |
| 插空、同学院老生、指定苑区 | 2 | 指定苑区内插空 |
| 插空、同学院老生 | 3 | 未指定苑区，且位于该批次自身主苑区 |
| 全空房、跨苑区 | 4 | 未指定苑区，但不在该批次自身主苑区 |
| 插空、兼容学院老生 | 5 | 普通可插空床位 |
| 研究生预留床位、兼容学院 | 5 | 仅床位锁定模式中的剩余床位 |
| 插空、不兼容学院老生 | 8 | 允许但不优先 |
| 指定苑区外全空房或普通床位 | 10 | 指定苑区容量不足的兜底总费用 |
| 研究生预留床位、不兼容学院 | 15 | 最后兜底 |

指定苑区外的 10 是该候选的总基础费用，不与“同苑区 1”或“跨苑区 4”叠加；否则同一业务含义会出现错误的双重罚分。对于未指定苑区的批次，主苑区必须由该批次自身的历史住户/容量适配或第一轮解独立确定，后续 LNS 可以重新选择；它绝不从同学院另一性别批次推导。若距离需要细分，统一用整数缩放后的附加费用，并确保不改变上述类别的优先顺序。

大量 0/1 费用会使多个方案完全同价，不能依赖求解器偶然的边遍历顺序。实现时将业务基础费用放大为固定倍率，再追加小于该倍率的稳定床位/房间排序值；响应中的业务成本仍按原表展示。这样同一输入和随机种子可复现，且任何 0 类候选仍严格优于任何 1 类候选。

### 不能使用的“整间边 + 部分边”技巧

不能为容量 C 的全空房并行建立“容量 C、费用 0 的整间边”和“容量 C-1、费用 20 的部分边”：

1. 两条并行边的总容量是 2C-1，会直接突破真实寝室容量；即使另设容量 C 的上游限制，也无法解决下一点。
2. MCMF 的容量是上限，不是“走了就必须走满”的下限。安排 k 小于 C 人时仍会走费用 0 的整间边，反而把部分入住误记为免费。
3. 纯 MCMF 的线性边费用不能表达“房间人数等于 C 时才奖励”或“同一学院占满才奖励”这类条件费用。

因此，MCMF 只保留一条总容量为 C 的真实寝室容量边，负责全员可行匹配和上述静态偏好。若首阶段就必须精确表达“整间使用或不使用”，需要引入 CP-SAT/MILP 的房间二元变量；本方案坚持 MCMF 作为可行性生成器，把该非线性目标交给后续 LNS/SA 精确评价，避免重新引入无法排满的风险。

## 可行性优先流程

    标准化床位、学生、锁定和策略
        → 硬约束容量证书
        → 空寝室性别识别与未知排除
        → MCMF：所有学生到合法床位
        → 局部 Repair 与完整校验
        → LNS：热点大范围拆除/重建
        → SA：合法邻域精调
        → 兼容快照、诊断与审计

### 1. 预处理与可行性证书

后端以当前 buildOccupancyModel() 的规则规范化输入，生成 Student、Bed、Room、Policy 四类不可变数据。先统计男女需求、固定性别房的可用容量、性别未知空房的容量、锁定/预留剔除量和研究生选定楼栋容量。

对性别未知的空寝室不做算法猜测：接口性别未知的寝室不进入候选图；操作者将楼栋临时设为 `unknown` 时，整栋全部可用床位同样排除。只有性别已知或明确临时设为男/女的全空寝室才进入候选图。

北苑学院性别互斥也是二元选择，不能只靠普通 MCMF 的线性容量边表达。预处理增加“北苑学院性别选择器”：每个学院在北苑只能选择男、女或均不进入三种状态之一；选择器以容量和批次需求为约束，固定每个学院在北苑可进入的性别后，再构建 MCMF 的学生到寝室边。若任何选择都无法覆盖需求，feasibilityCertificate 必须报告北苑学院性别互斥造成的缺口，而不能先生成违法方案再寄望 LNS 修复。

若无法满足硬约束，不返回笼统的“排不进去”，而返回 feasibilityCertificate：需求、各类可用容量、最小割/缺口、造成缺口的锁定/预留/性别/研究生范围，以及可操作的修复建议。学院兼容和插空比例不能出现在该证书的无解原因中。

### 2. 最小费用流生成全局初始解

采用无第三方求解器依赖的 Python 最小费用最大流，以学院 × 性别 × 学历批次聚合节点降低规模；传入真实学生时可按学生节点展开。

    Source → 学生批次/学生 → 寝室可用容量节点 → Sink

- Source 到学生的容量为需求，所有学生流量必须达到需求总数；图中不设置“未安排”成功出口。
- 学生到寝室仅在性别、可用状态、锁定、预留、校区/研究生范围和北苑学院性别选择均合法时建边。
- 寝室到 Sink 容量为真实可用床位数，保证床位不重复和寝室不超容。
- 边费用采用“已确认的 MCMF 边费用”表，表达历史学院亲和、指定苑区、插空类别和研究生优先/后备床位；学院间的计划混住、同学院占满空房和空房未住满等非线性房间费用由后续阶段处理。

流量等于总需求才接受方案。这样贪心顺序不会再提前消耗另一批学生的唯一候选床位；只要硬约束下存在全量匹配，就一定得到初始解。

### 3. Repair

MCMF 输出后立即映射为真实 bedId 和现有快照字段，再执行统一硬校验。Repair 仅处理床位映射、计划摘要与局部重建等一致性问题；不能把可行方案改为不完整方案。它的结果仍必须是全员已安排。

### 4. LNS 大范围重组

以成本热点选择 1 至多个关联寝室/学院/楼栋作为 destroy 邻域：原全空房中混住的新生、单人空寝、学院跨苑区分散、超插空目标、研究生落入后备楼栋等。暂时释放该邻域学生和床位，保留其余方案为固定约束，再在残余图上运行 MCMF rebuild。

采用多种邻域尺度与随机种子；只接受通过完整硬校验的候选。若候选优于历史最优则保留，非最优候选可按退火准则暂存以跳出局部最优。LNS 负责跨多个寝室的整体重排，弥补单人迁移无法跨越的局部障碍。

### 5. 模拟退火精调

在 LNS 之后继续使用可复现实验种子的模拟退火。邻域包括单人迁移、同性交换、同学院整批迁移、全寝合并、两/多寝室 ejection chain；每次操作均调用硬校验，其中北苑每个学院的计划性别集合必须至多一个。温度从当前成本权重自适应计算并几何降温，始终保存历史最优快照。返回尝试数、合法候选数、接受的上坡次数、LNS 改善次数、初始/最终成本和随机种子。

### LNS/SA 的房间级目标

原来的“单人空房、空房碎片、学院分散”不能识别一间原全空四人房被安排为 3 个学院 A 新生和 1 个学院 B 新生：该房已住满、没有碎片，也不会触发单人房罚分。为此新增原全空房学院纯度指标：

    foreignStudents(room) = plannedStudents(room) - max(同一学院在该房的计划人数)
    emptyRoomForeigners = Σ foreignStudents(room)，仅统计 originalState 为 EMPTY 的房间

同学院住满时该值为 0；3A + 1B 的值为 1；2A + 2B 的值为 2。LNS destroy 必须优先选择该指标大于 0 的房间，并将该房、新生所属学院的其他床位和可交换同类房间放进同一 rebuild 邻域。

当前实现以远高于分散、碎片和插空项的房间纯度费用驱动 LNS/SA：只要存在保持硬约束的替代床位，`3A + 1B` 会优先被拆开；单人空房仍为次一级高权重目标。后续若学生规模增长到可能让低优先级总和抵消该费用，应升级为字典序成本向量，而不是继续提高常数。

插空上限按学院 × 性别 × 学历批次计算，而不是使用量纲不一致的“全局实际比例减全局上限”：对批次 b，超额人数为 max(0, partialBeds_b - ceil(studentCount_b × maxVacancyRatio_b))，总代价取各批次超额人数之和。批次间插空比方差使用学生人数加权方差，避免 1 人小学院的 100% 插空率主导整个方案。全局平均插空比只作为中等优先级的总量指标。

## Flask 服务设计

当前服务已位于前端仓库的 `allocation_service/`；不要把 Python 算法嵌入 Vue worker。

    allocation_service/
      app.py
      solver/min_cost_flow.py
      solver/planner.py
      solver/improver.py
      tests/
      requirements.txt

- POST /api/allocation/v1/solve：标准化、可行性证书和 MCMF，同步返回全员初始方案。
- POST /api/allocation/v1/improve：接收同一份输入，重建初始解后运行 Repair、LNS 和 SA，返回历史最优快照、成本和搜索摘要。
- 首期可由前端继续加载床位后将输入传给 Flask；生产阶段应由服务端以权限和库存版本读取权威床位数据，并返回 inventoryVersion，确认前再次校验版本以避免并发占床。

当前仅依赖 Flask 与标准库。开发时运行 Flask；生产用合适的 WSGI 服务器和独立任务执行器运行长时间的 LNS/SA。服务端日志仅保存脱敏统计、请求 ID 和随机种子，不打印学生个人信息。

## 前端单一全局算法接入

### 交互设计

页面不再提供贪心算法选择。本科生和研究生均使用 Flask 的全局 MCMF 服务，按钮分别显示“生成全局方案”和“生成研究生全局方案”。原“学院混住策略”及“跨学院成本”完全移除；兼容关系编辑保留，作为新服务的同学院/兼容/不兼容床位边费用输入。

本科生命令条改为只读的引擎状态：“MCMF · 全局可行”与“未知楼栋不参与安排”。它与原有高密度深色工作台保持一致，移动端独占一行。结果区域展示安排人数、流网络费用、因临时未知而排除的床位数及北苑性别互斥分支数。

楼栋临时性别增加“临时设为未知（不参与安排）”。它不同于“使用接口配置”：前者排除整栋的全空房和部分入住寝室中的所有可用床位，后者继续使用接口性别和现有住户性别。

### 前端模块边界

BedAllocationNewView.vue 继续只承担页面状态、参数、锁定、热力图和预览协调，不加入任何 MCMF/LNS 细节。新增下列前端文件：

    src/api/allocationPlanning.js
      Flask 的 solve、improve 请求与响应规范化
    src/features/allocation/allocationSnapshotMetrics.js
      从服务端兼容快照读取页面容量指标

现有 bedAllocationNew.js 与两个 worker 不再被页面调用，只作为遗留测试基线；不要向该文件继续加入新算法。待 MCMF、Repair、LNS 和 SA 完成同输入回放与快照兼容验证后删除。

Flask 的 MCMF、Repair、LNS、SA、北苑选择器和硬校验全部建立新文件，不复制或续写前端贪心逻辑：

    allocation_service/

## 验收与回归

1. 新增“原贪心失败、全局可行”的最小样例：多个学院/性别均有总容量，但顺序插空或整间优先会卡死；新方案必须全员安排。
2. 男女需求在硬容量上确实不足时，必须失败并给出性别/锁定/预留/范围的精确证书。
3. 性别未知空房不得进入候选图；临时设为未知的楼栋必须完整排除，且快照中不能产生男女同寝。
4. 锁定研究生、整间/床位锁定、研究生优先到后备楼栋、指定苑区范围等硬约束在 MCMF、LNS、SA 后均不被突破。
4.1. 同一学院的男女批次不能同时出现在北苑；该条件在 MCMF 前的选择器、完整校验、LNS rebuild 和 SA 每个邻域操作后均验证。
5. 学院不兼容、最大插空比、主苑区偏好和整间住满在容量充足时优化良好，在容量紧张时可以付费突破且不再导致无解。
6. 对当前 test/bedAllocationNew.test.js 的样例和脱敏真实库存回放：新求解器的可安排人数不得低于旧算法；完整可行样例必须为 100%。
7. 校验快照可被当前热力图、预览和 Excel 导出消费；固定随机种子下结果和成本可复现。
8. 四人原全空房出现 3A + 1B 时，若 B 存在保持硬约束的替代床位，LNS/SA 必须将其重排为学院纯度更高的方案；若不存在替代床位，诊断需明确标记该混住为不可避免的软目标妥协。

## 预期结果与最差情形

### 正常的硬约束可行场景

服务首先返回全员已安排的 MCMF 初始方案；LNS 和 SA 随后重排并输出历史最优方案。最终结果满足性别、真实床位容量、可用状态、锁定、预留和学历/楼栋范围，且优先形成同学院新生住满原全空房的组合，再减少单人空房、插空超额、学院分散和跨区安置。响应同时包含初始/最终成本、各软目标妥协量、随机种子和每项混住的原因。

### 硬约束可行但资源结构很差

系统仍然必须安排所有人；它可以突破学院兼容、最大插空比、指定苑区、优先楼栋和整间住满等软目标。此时可能出现跨苑区、跨学院插空、部分空房和较高插空比，但绝不出现男女混住、超床位、占用不可用床位或突破锁定/硬预留。没有替代床位时，3A + 1B 也可能保留，并被标记为“学院纯度不可避免的软目标妥协”，而非静默当作最优。

### 真正的最差情形：硬约束无解

原始总床位数大于人数仍不保证可行：例如男生可用容量不足、所有余床被锁定/硬预留、研究生选定楼栋范围不足、床位不可分配，或输入缺少可验证的性别/床位标识。此时服务不产生伪完整方案，而返回 feasibilityCertificate，精确列出缺口和造成缺口的约束；学院兼容、插空比例、苑区偏好和房间纯度永远不会成为无解理由。

### 优化时间受限

若 LNS/SA 达到时间或迭代上限，立即返回已经全员可行的 MCMF/Repair 方案，并标记 optimizationTimedOut。搜索可以临时接受更差候选，但对外只返回历史最优快照，因此最终结果不会劣于该次的可行初始方案。
