# `/accommodation/bed-allocation-new` 智能排寝算法实现说明

## 1. 实现位置与产物

- 页面编排：`src/views/BedAllocationNewView.vue`
- 床位/入住标准化：`src/features/accommodation/occupancyData.js`
- 本科生、研究生分配与优化：`src/features/allocation/bedAllocationNew.js`
- 预览/导出聚合：`src/features/allocation/bedAllocationPreview.js`
- 可脱离 Vue 重放的参考脚本：`outdoc/bed_allocation_core.py`

页面只在浏览器本地生成快照，不直接写入宿管业务库。快照中的 `assignments` 是逐床位的模拟结果；`rooms[].allocations` 是为热力图、预览和导出保留的房间聚合结果。

## 2. 输入标准化与硬约束

`buildOccupancyModel` 先把 API 返回的床位行按房间聚合。一个床位只有同时满足以下条件才进入可分配池：状态为 `AVAILABLE`（兼容“可用/空闲/空床”）、`assignable`、`active`、`roomAssignable`、`roomActive` 均为 `true`，且没有入住状态或当前学生编号。房间状态由当前入住数决定：`EMPTY`、`PARTIAL`、`FULL`。

分配时的硬约束为：

1. 房间性别必须与学生性别一致。楼栋性别字段优先于房间性别字段；已知异性入住者会使房间不能混住。
2. 学院兼容策略按校区本地保存，默认“严格”：房间已有历史学院和本次已安排学院必须与新学院兼容。同学院隐式兼容；兼容矩阵判断是对称的；历史学院未知时按最低优先级放行，已知不兼容则拒绝。管理员可改为“距离优先宽松插空”：仅本科生普通 `PARTIAL` 房在严格候选完全耗尽后，才可忽略学院兼容；性别、容量、锁定、预留、研究生房和插空上限仍是硬约束。
3. 预留的全空房、研究生锁定房或锁定床不能被本科生占用。
4. 每个本科批次（学院 + 性别）的插空人数不能超过当前目标整数床位数。

### 2.1 临时楼栋性别与男女容量预检

本科生工作台的“楼栋性别”入口提供按校区保存的临时男生楼/女生楼设置，仅保存在浏览器 `localStorage`，不会写回宿舍或床位接口。它用于预估楼栋改造后是否能消除男女床位的物理缺口，并会随生成的方案快照保存，后续局部优化仍使用同一套假设。

- 原始状态为 `EMPTY` 的房间优先采用临时楼栋性别；未设置时使用接口返回的楼栋性别。
- 原始状态为 `PARTIAL` 的房间优先且固定采用已入住学生的性别，不受临时设置影响；若已入住学生性别缺失，才退回接口楼栋性别；已知混合性别或无法判断的部分入住房间不参与插空。
- “学生参数”和“楼栋性别”弹窗都显示本科男/女输入总数与物理上限。物理上限由可分配的全空床位（按临时或接口楼栋性别）和可分配的部分入住床位（按现住学生性别）组成；未识别性别的空房和不可判定插空床位单列，不计入任何一方。

当某性别的输入人数大于其物理上限时，当前数据下必然无法安排，必须增加该性别床位或通过临时楼栋设置模拟改造后再计算。输入不超过上限只说明性别物理容量没有直接矛盾，并不保证一定可排入，因为预留、锁定、学院兼容、插空上限和苑区均衡仍会缩小实际可用集合。

## 3. 本科生算法

### 3.1 批次与学生

页面把输入拆成 `(collegeId, gender, undergraduate)` 批次。人数取非负整数，最大插空比 `ρ_max` 限制在 `[0,100]`，最大插空床位为：

```text
max_target = ceil(count × ρ_max / 100)
```

未传真实学生时生成稳定的虚拟学生 ID；传入 `students` 时按学生 ID 排序，优先使用真实学生，不足部分再补虚拟学生。

### 3.2 阶段一：普通全空房贪心

批次按“存在同容量全空房优先、人数降序、学院名、性别”排序。每个学院-性别行可以填写“指定苑区”，该值按苑区 ID（没有 ID 时按名称）保存到批次。未指定苑区时，系统先为批次从所有苑区计算主苑区：优先选择可覆盖该批次人数且总容量差值最小的苑区，再以可连续使用的楼栋数量作为次级评分，完全相同才使用批次稳定哈希打破平局。因此苑区名称和中文排序不会形成固定优先级。全空阶段只选择当前剩余人数能够整间住满的普通空房，并连续填满该房间；例如 6 人面对 4 人间时，先安排 4 人住满一间，剩余 2 人留给插空阶段，而不会新开一间只住 2 人的空房。

1. 性别和兼容性可行；
2. 未被预留、锁定且不是研究生房；
3. 指定苑区是人工优先选择：即使该苑区只剩容量更大的空房，也允许在指定苑区安排尾数；
4. 其余情况按房间剩余床位数与当前剩余人数的绝对差排序（差值小者优先），再按剩余床位数、楼栋/房号自然序稳定打破平局。

这样可最大化整间住满的空房数量，同时保持确定性。

### 3.3 阶段二：普通插空

全空阶段未安排的学生进入插空阶段。每个批次最多使用 `target` 张原始状态为 `PARTIAL` 的床位。候选房按以下优先级排序：

1. 该批次已经使用过的楼栋；
2. 已使用楼栋所在苑区的其他楼栋；
3. 其他苑区；
4. 房间历史学院与当前学院相同；
5. 有兼容历史学院；
6. API 距离字段较小者、剩余床位少者、房号自然序。

成功后实时更新批次的楼栋/苑区足迹，故后续学生会尽量向已形成的居住范围集中。

严格策略只从兼容候选中选择。“距离优先宽松插空”会先遍历全部严格兼容候选，即使严格候选更远也不会被附近不兼容房间抢占；严格候选完全耗尽后，才在同样的楼栋/苑区圈层和距离排序下选择学院不兼容、但其余硬约束均合格的普通部分入住寝室。该分配仍标记为 `allocationType: 'partial'`，另以学生级 `compatibilityMode: 'relaxed'` 和明确原因记录；诊断分别显示严格可插空床位、宽松插空可用床位及已用床位，并列出宽松插入的房间、涉及学院和历史学院。全空房及研究生房后备始终保持严格兼容。

### 3.4 阶段三：研究生房后备

若 `graduateFallback.enabled` 为真，仍未安排的本科生可以进入标记为研究生房的任意可用房间。此阶段仍检查性别与学院兼容，不再使用本科批次的苑区圈层；仍未安排的学生继续进入空房兜底检查。

### 3.5 未满空房兜底

按输入最大插空比不能完成安置时，系统先保持当前学院混住策略和输入上限不变，允许开启未住满的普通空房处理尾数；因此“距离优先宽松插空”可以与尾数空房兜底共同生效。若仍不能完成，才进入物理可行性插空路线，优先使用严格兼容插空床位；即使实际比例因此超过输入上限，也会在诊断中明确提示。此类未满空房分配标记为 `empty-overflow`，以便在快照中与整间住满的空房安排区分。

## 4. 插空比自动校准

先用所有批次的 `max_target` 做一次完整仿真。仿真成功后，直接从实际分配结果汇总每个批次进入原始部分入住寝室的学生数，作为 `targetBeds`；这避免了按批次反复从零模拟整套方案，在千人规模下仍可快速给出结果。快照同时记录 `targetBeds`、`maxBeds`、`actualRatio` 和 `maxRatio`。

若按全部 `max_target` 的常规仿真仍不可行，系统会先以相同目标和当前策略开启一次未满空房兜底仿真；该步骤成功时，宽松插空和尾数空房均不会突破管理员输入的上限。若仍不可行，系统才会用每批次全部人数作为插空上限做一次物理可行性仿真。该最后兜底仅使用严格兼容插空床位，避免距离优先宽松插空在管理员设定的上限之外继续扩张；仿真可行时，直接汇总实际使用的插空人数，并在 `diagnostics.overRatioFallbacks` 中逐批次记录超出输入上限的床位数和实际比例；页面会提示“安置兜底”。若这一步仍不可行，才说明性别、锁定、预留、学院兼容或真实可用床位不足，诊断会列出未安置人数、插空/全空可用床位和失败原因。

## 5. 研究生独立方案

研究生在参数表中按“学院 × 性别”填写人数和最大插空比，批次键为 `(collegeId, graduate, gender)`。操作员选择的优先楼栋和后备楼栋路径会按输入顺序合并去重；只允许使用这些楼栋，且必须先处理优先楼栋，再进入后备楼栋。

每个楼栋内复用本科生的核心阶段：先用可整间住满的 `EMPTY` 房，再在该学院兼容、性别正确的 `PARTIAL` 房内使用不超过该批次最大值的插空床位，最后才将无法整间住满的尾数放入 `EMPTY` 房。学院兼容矩阵同样生效；研究生不启用本科生的距离优先宽松插空、研究生房后备或超出最大插空比的兜底。快照按学院保留逐床位 `assignments`、每批次实际插空比以及优先/后备楼栋键顺序，预览和 Excel 导出也按学院、性别聚合。

研究生方案可按“锁房间”或“锁床位”持久化。锁定状态会在之后的本科模拟中重新应用，防止本科方案覆盖已确认的研究生资源。

## 6. 代价函数与局部交换

本科分配完成后计算：

```text
zoneSpread     = Σ_college max(0, 使用苑区数 - 1)
crossZone      = Σ_college 不在该学院主苑区的学生数
buildingSpread = Σ_college max(0, 使用楼栋数 - 1)
roomSpread     = Σ_college max(0, 使用房间数 - 1)
emptyFragment  = 原始全空房未使用床位数
fragmentedRoom = 有分配但未住满的原始全空房间数
singletonRoom  = 原始全空房中仅安排 1 人的房间数（四人寝单人房重点惩罚）
crossCollegeCount = 本科生所在房间中存在已知、非同学院且未配置兼容的历史或本次学院的学生数
totalCost      = 100×zoneSpread + 10×crossZone + 1×buildingSpread
                 + 4×roomSpread + 0.1×emptyFragment
                 + 2×fragmentedRoom + 35×singletonRoom
                 + crossCollegeWeight×crossCollegeCount
```

`crossCollegeWeight` 按校区本地可调，默认 `10`，并随快照保存。优化器是带新随机种子的局部搜索：每次点击“优化方案”都会生成不同的搜索轨迹，默认尝试单人迁移、同性别双人交换和原子寝室合并。迁移会从当前学生所在房间释放一张模拟床位，再从原始床位库存中选择同性别、可用、未预留和未锁定的目标床位；它可进入未在初始方案中启用的普通空房。目标优先已有该学院学生且更满的房间，再考虑学院主苑区。对于原始全空房，不允许把较满的同学院房间迁成更空的房间，避免 `3+1` 这种局部最优陷阱。

原子寝室合并把一个未住满全空房中的全部本科生，一次性迁入容量足够、学院兼容的另一个已启用全空房。它专门处理 `2+2 -> 0+4`：若拆成单人迁移，第一步会出现 `1+3` 并触发单人房惩罚，严格下降爬山会拒绝这一步；作为一个整体评估后则可直接接受成本下降的满房结果。交换也会同步运行态房间成员，保证后续迁移继续按真实在住学生检查兼容关系。距离优先宽松插空快照会优先抽取当前跨学院混住学生作为候选；迁移仅可宽松进入普通部分入住寝室，交换可在两间部分入住寝室容量不变的前提下消除混住，全空房和研究生房始终严格。每轮优化结束都会按房间的实际历史住户和本次成员重新计算宽松标记与混住诊断，不能只沿用初始标记。三种邻域操作后都必须重新满足学院兼容（距离优先宽松插空的上述例外）、插空目标、北区均衡和锁定/预留约束；只有 `totalCost` 严格下降才接受。默认最多尝试 5000 次，连续 1000 次无改善即停止。由于只接受下降，成本单调不升；“未找到改进”仅表示本轮搜索未改善，不能推导为全局最优。

## 7. Python 参考脚本

脚本不依赖第三方库：

```powershell
python outdoc/bed_allocation_core.py input.json -o snapshot.json
```

调试时也可以把 JSON 通过标准输入传入：`Get-Content input.json -Encoding utf8 | python outdoc/bed_allocation_core.py -`。脚本标准输出会强制使用 UTF-8，便于 PowerShell 7 管道和审计工具读取。

最小输入示例：

```json
{
  "rooms": [{
    "room_key": "r-101", "room_code": "101", "building_key": "b-1",
    "building_name": "一栋", "zone_key": "z-s", "zone_name": "南区",
    "gender": "male", "total_beds": 4, "occupied_beds": 0,
    "available_beds": ["r-101-1", "r-101-2", "r-101-3", "r-101-4"],
    "historical_colleges": [], "is_graduate": false
  }],
  "undergraduate": [{"college_id": "c-1", "college_name": "计算机学院", "gender": "male", "count": 4, "max_ratio": 0, "preferred_zone_id": "z-s"}],
  "compatibility": {}, "graduate_fallback": true
}
```

输出包括 `success`、每批次校准后的 `targets`、逐床位 `assignments`、房间资源和短缺列表；有研究生配置时还会增加 `graduate` 结果。该脚本是算法参考/回放工具，不替代前端 API 字段标准化和页面锁定交互。

## 8. 验证

前端已有 `npm test`（当前 34 个 `node:test` 用例）和 `npm run build`。距离优先宽松插空覆盖严格拒绝、严格候选优先、性别/研究生房/插空上限、与尾数空房兜底组合、历史与本次跨学院成本，以及迁移和满房交换消除混住；楼栋临时性别覆盖了本科和研究生空房生效、部分入住房以真实住户性别优先和快照保留；研究生覆盖学院批次和优先楼栋耗尽后进入后备楼栋。新增脚本可用：

```powershell
python -m py_compile outdoc/bed_allocation_core.py
git diff --check
```
